# VLM 耗时分析：一次识别的时间花在哪里？两辆车同时请求会怎样？

测试日期：2026-11-14（酒店网络 `hyatt`）。所有数字都是实测值，没有估算的地方会标明“估计”。

## 0. 测试条件

| 项目 | 设置 |
| --- | --- |
| VLM 电脑 | MacBook Air M4，16 GB（**无风扇**，长时间满负荷会降频，见第 5 节） |
| 推理服务 | llama.cpp `llama-server`（build b12110，Homebrew 0.9.0），`-ngl 99 -c 8192 --image-max-tokens 1024` |
| 模型 | `ggml-org/Qwen2.5-VL-3B-Instruct-GGUF`：语言模型 Q4_K_M，视觉编码器（mmproj）Q8_0 |
| 小车 | B 车（Raspberry Pi 5），通过酒店 Wi-Fi 连 Mac（`172.20.1.112:8090`） |
| 图片 | 车载摄像头 640×480，按车上 `vlm.py` 的规则缩到 ≤400 个视觉 token，即 **644×476**，JPEG 质量 92，约 69 KB |
| 提示词 | 车上 `vlm.py` 的 `PROMPT_ANY`（“框出桌面/地面上所有物体”），与比赛时一致 |
| 防缓存 | 每次请求都在图片角上改 8×8 个随机像素。**只改 1 个像素不够**：llama-server 仍会命中缓存，耗时会从 3.1 秒降到 0.97 秒，数据就不真实了 |

## 1. 一张图 3.1 秒都花在哪了（单辆车，Qwen2.5-VL 3B + llama-server）

从 B 车实际发请求到 Mac 测得（`bench/car_timing.py`，6 次，取中位数），服务器内部各段的时间来自 llama-server 自带的计时和详细日志（`-lv 4`）。

| # | 阶段 | 在哪里运行 | 耗时 | 占一次请求的比例 | 怎么测的 |
| --- | --- | --- | --- | --- | --- |
| 0 | 拍照：`snap()` 打开摄像头 + 读 10 帧等自动曝光 | 车 | **0.61 – 0.75 s** | （在请求之外） | 在车上按 `snap()` 的方式计时 |
| 1 | 缩图 + JPEG 编码 + base64 + 组 JSON | 车 | **5 ms**（第一次 26 ms） | <1% | 车上计时 |
| 2 | Wi-Fi 上传约 93 KB + 返回 + HTTP 开销 | 网络 | **0.10 – 0.28 s**，中位数 0.17 s；**偶尔 4 s** | ~5% | 车上总时间减去服务器计时；ping 平均 37 ms，最大 172 ms |
| 3 | 解码 JPEG、整理图片 | Mac CPU | 几 ms | <1% | 日志 |
| 4 | 前 15 个文字 token（对话模板）预填充 | Mac GPU | ~2 ms | <1% | 日志时间戳 |
| 5 | **视觉编码器**（ViT）：图片 → 391 个视觉 token | Mac GPU | **~1.05 s** | **~33%** | 日志：`encoding mtmd batch` → `decoding image batch` 两行之间 |
| 6 | **语言模型预填充**：391 个视觉 token + 81 个提示词 token | Mac GPU | **~1.07 s** | **~34%** | `prompt_ms`（2.14 s）减去第 5 段；另用 482 个 token 的纯文字请求验证：1.06 – 1.08 s（约 450 token/s） |
| 7 | **生成回答**：约 41 个 token，每个 23.5 ms | Mac GPU | **~0.95 s** | **~30%** | `predicted_ms`；约 42 token/s |
| | **合计：服务器端**（第 3–7 段） | | **3.1 s** | | `prompt_ms` + `predicted_ms` |
| | **合计：车上看到的一次请求**（第 1–7 段） | | **3.2 s**（偶尔 7 s） | | 车上计时 |
| | **合计：拍照 + 请求** | | **约 3.8 – 4.0 s** | | |

几点说明：

- **三大块差不多各占三分之一**：看图（视觉编码）、读题（预填充）、写答案（生成）。网络只占约 5%，但酒店 Wi-Fi 偶尔会突然卡到 4 秒。
- **答案里一半是“废话”**：模型的回答是 `` ```json [ {"bbox_2d": [385, 445, 677, 726], "label": "short name"} ] ``` ``，共约 41 个 token。真正有用的只有 4 个坐标，代码块标记（```` ``` ````）和 `"label": "short name"` 也算在生成时间里。
- **没东西时快约 1 秒**：回答是 `[]`，只有几个 token，生成几乎不花时间，总共约 2.2 秒。
- **第一次请求会慢**：服务器空闲一段时间后的第一张图花了 6.3 秒（预填充 5.1 秒），之后恢复正常。比赛开始前最好先发一张图预热。
- **摄像头**：`find` 和 `grab` 每拍一张照片都要重新打开摄像头并读 10 帧，约 0.6 – 0.75 秒。`approach` 用的 `Cam` 类会一直开着摄像头，没有这个开销。

## 2. 不同服务器 / 模型对比（同一台 Mac、同一批 25 张照片，`bench/vlm_bench.py`）

| 方案 | 每张新图（中位数 / p90） | 有物体找到 | 空照片误报 | 备注 |
| --- | --- | --- | --- | --- |
| **llama-server + Qwen2.5-VL 3B** | **3.1 s / 3.3 s** | 15/16 | 0/9 | 坐标就是原图像素，车上代码不用改 |

| Ollama + qwen3-vl:2b，Junbo 的 448×336 设置 | 4.5 s / 5.0 s | 12/16 | 0/9 | 图缩小了并不更快：Ollama 会把它再放大 |

## 3. 两三辆车同时请求（`bench/concurrency.py`）

在 Mac 本机模拟多辆车（每辆车一个线程），每辆车发 8 张新图。车到 Mac 的网络约 0.1 – 0.3 秒，没算在下面的数字里。

- **sync**：每一轮所有车**同时**发出请求，是最坏情况。
- **stagger**：每辆车两次请求之间随机停 0 – 3 秒，更接近真实情况。

“先到 / 后到”指每一轮里先拿到答案和后拿到答案那辆车的等待时间（中位数）。**两个数字都从同一时刻算起**（两辆车同时发出请求），后到那辆的时间已经**包含**排队等前一辆的时间，不能相加：例如 “2.5 s / 4.1 s” 表示这一轮两辆车都拿到答案共用了 4.1 s。

| 服务器配置 | 车数 | 模式 | 每次请求（中位数 / p90） | 先到 / 后到 | 吞吐量 |
| --- | --- | --- | --- | --- | --- |
| llama-server **4 个并发槽位**（= 你 Mac 上 8090 现在的配置） | 1 | — | 3.8 s / 4.1 s | — | 16 次/分钟 |
| | 2 | sync | 6.2 s / 6.8 s | **5.4 s / 6.4 s** | 19 次/分钟 |
| | 3 | sync | 9.2 s / 10.2 s | 8.2 s / 9.5 s | 19 次/分钟 |
| | 2 | stagger | 4.8 s / 8.3 s | — | 17 次/分钟 |
| llama-server **1 个槽位（排队）**，`-np 1` | 1 | — | 3.6 s / 4.6 s | — | 17 次/分钟 |
| | 2 | sync | 4.5 s / 7.1 s | **3.5 s / 6.4 s** | 19 次/分钟 |
| | 3 | sync | 6.9 s / 11.0 s | 3.2 s / 10.4 s | 17 次/分钟 |
| | 2 | stagger | 5.0 s / 6.4 s | — | 17 次/分钟 |
| Ollama + qwen3-vl:2b（Ollama 默认会排队） | 1 | — | 4.9 s / 5.1 s | — | 12 次/分钟 |
| | 2 | sync | 7.6 s / 10.8 s | 5.2 s / 10.3 s | 12 次/分钟 |
| | 3 | sync | 10.9 s / 17.0 s | 5.5 s / 16.4 s | 11 次/分钟 |
| | 2 | stagger | 9.2 s / 10.3 s | — | 11 次/分钟 |

结论：

1. **不会出错，只会变慢。** 所有请求都正常返回，没有丢失，也没有串到别的车。
2. **GPU 已经满负荷，开多个槽位不会更快。** 不管几辆车、几个槽位，llama-server 都是每分钟约 17 – 19 个回答。多个槽位只是让几个请求一起慢下来：两辆车同时发，4 槽位时**两辆车都要等 5.4 – 6.4 秒**。
3. **排队（1 个槽位）对缩短总时间更有利。** 两辆车同时发时，先到的车 3.5 秒就拿到答案、可以继续动作；后到的车 6.4 秒，和 4 槽位时一样。平均等待从 5.9 秒降到 5.0 秒。所以给多车用的服务器建议改成 `-np 1`。
4. **两辆车真正同时请求的情况不多**：一次抓取只调用 2 到 4 次 VLM（找物体一次，追丢了再找，抓之前确认位置），中间大部分时间在开车、动机械臂。stagger 模式下，2 辆车的中位数是 4.8 – 5.0 秒，比单车多约 1.2 秒。
5. **三辆车就明显吃力了**：最慢的车要等 10 秒以上。如果 C 车（推土车）将来也要用 VLM，需要更快的配置（见第 4 节），或者第二台电脑。

## 4. 提速办法：实测结果

同一台 Mac，llama-server + Qwen2.5-VL 3B，同一批 25 张照片，每张都是新图（`vlm_bench.py`）。这一组是同一时段连着跑的，所以可以互相比较。

### 4.1 视觉 token 数（车上 `vlm_server.json` 的 `img_tokens`）✅ 采用 256

| `img_tokens` | 实际送进模型的图 | 输入 token | 读题（prompt_ms） | 每张新图（中位数 / p90） | 有物体找到 | 空照片误报 | 框和 400 档相比的偏差（640×480 像素：中位数 / 最大） |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 400（现在） | 644×476 | 487 | 2155 ms | 3.07 s / 3.41 s | 15/16 | 0/9 | — |
| 320 | 560×420 | 396 | 1990 ms | 2.92 s / 3.12 s | 16/16 | 0/9 | 1 / 3 px |
| **256** | **504×364**（实际 234 个视觉 token） | **330** | **1516 ms** | **2.46 s / 2.70 s** | **15/16** | **0/9** | **2 / 5 px** |
| 192 | 448×336 | 288 | 1637 ms | 2.68 s / 2.89 s | 15/16 | 0/9 | 2 / 6 px |

- 256 比 400 **快 0.6 s（−20%）**，找到的数量和误报都一样。
- 框最多偏 5 个像素。按 B 车的标定（`vision_calib.json` 的单应矩阵，约 0.03 cm/像素），也就 1 – 2 mm，对抓取没有影响。
- 再降到 192 不会更快：读题时间没有继续下降，生成反而多了几个 token。
- 车上只要改配置，代码不用动：`"img_tokens": 256`。服务器的 `--image-max-tokens 1024` 不用改。

### 4.2 让模型少输出（提示词后加一句）❌ 不采用

| 追加的提示词 | 输出 token | 每张新图 | 有物体找到 |
| --- | --- | --- | --- |
| （无，车上原样） | 41 | 2.46 s | 15/16 |
| “Reply with the JSON array only: no code block, no other text.” | 35 | 2.59 s | **13/16** |
| 同上 + “Use a one-word label.” | 33 | 2.74 s | **13/16** |

生成只省了约 0.1 s，但提示词变长、读题更慢，**找到的数量还变少了**。车上的提示词保持不变。

### 4.3 多车时服务器只开 1 个槽位（`-np 1`）✅ 采用

和 4.1 的 256 token 组合后（`concurrency.py --tokens 256`）：

| 配置 | 1 辆车 | 2 辆车同时：先到 / 后到 | 2 辆车随机错开（中位数 / p90） | 吞吐量 |
| --- | --- | --- | --- | --- |
| 现在：400 token，4 个槽位 | 3.8 s | 5.4 s / 6.4 s | 4.8 s / 8.3 s | 17 – 19 次/分钟 |
| **256 token，1 个槽位** | **2.4 s** | **2.5 s / 4.1 s** | **2.7 s / 3.3 s** | **26 – 28 次/分钟** |

两辆车同时请求时，后到的那辆也只要等 4.1 秒，比现在先到的那辆（5.4 秒）还快。4.1 s 是从两辆车同时发出请求算起的，已经包含排队时间，不是在 2.5 s 之后再加 4.1 s。它比单车时间的两倍（4.8 s）短，可能是因为第二个请求的一部分准备工作（接收、解码图片）和第一个请求同时进行了；这个原因还没有验证。

### 4.4 拍照时不重复开关摄像头 ⏸ 已测，还没改车上的代码

在 B 车上测（`snap()` 的打开方式，V4L2，`CAP_PROP_BUFFERSIZE=1`）：

| 做法 | 每张照片 |
| --- | --- |
| 现在的 `snap()`：每次打开摄像头 + 读 10 帧 | 610 – 750 ms |
| 摄像头一直开着；拍照时先丢掉缓冲区里那 1 帧旧画面，再取一帧新的 | **80 ms**（4 次都一样：第一次 grab 0 ms 是旧帧，第二次 79 ms 是新帧） |

每张照片约省 0.6 s，`find`/`grab` 一次抓取要拍 2 到 4 张。改 `vlm_grab.py` 时要注意：
- `approach` 里的 `Cam` 类会另外再打开同一个摄像头，必须改成两边共用一个，否则会报设备占用。
- **一定要先丢掉旧帧**：摄像头一直开着时，缓冲区里会留着机械臂移动之前的画面。直接读就会把旧画面送给 VLM。
- 改完要让机械臂真的动起来测一遍（`look` → `find` → `grab`），需要有人在车旁边。

## 5. 测量可靠性

- 并发测试是按顺序跑的，后面几组跑的时候机器已经热了。可以看到单车基准从 3.1 s 涨到 3.6 – 3.8 s，所以各组之间的比较有约 ±15% 的误差。同一组里“先到 / 后到”的对比不受影响。
- 测试集里只有积木、标定卡片和空桌面（来自 B 车 11-12、11-13 的照片），**没有真正的垃圾**（瓶子、易拉罐、纸团），地毯也只有 1 张。准确率要用比赛现场的照片再测一次。
- 车到 Mac 的网络是酒店 Wi-Fi。换成自己的路由器后要重测第 2 段。
